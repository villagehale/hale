# Review guide

Read by Devin Review and by every agent that reviews a pull request here.

**What is severe: the hard rules in `CLAUDE.md`.** Read them before reviewing:
- privacy and teen data;
- consent before any autonomous action;
- two-parent consent;
- the immutable audit row;
- spending caps;
- additive migrations;
- prompts loaded by name;
- named outcomes for an absent dependency.

Treat as severe any change that weakens one of them, and any new path that bypasses the code enforcing one. The code's own comments say how each rule is enforced. **This repository is public:** flag any real name, phone number, email or id in code, fixtures, PR text or commit messages.

## Intended: don't flag these as bugs

- **Marketing measurement by region.** On villagehale.com, Quebec (Canada, province QC), the EU, the EEA, the UK, and Switzerland stay opt-in. A missing country, Canada with no province, and the unknown-country codes stay opt-in. Everywhere else the first visit loads the Meta Pixel, Google Ads, PostHog (analytics and session replay), and the first-party attribution cookie, and the banner is a notice with Turn off. Global Privacy Control (`Sec-GPC: 1` or `navigator.globalPrivacyControl`) blocks that default until the visitor taps Accept. A stored Turn off or No thanks stays off. A stored Accept stays on, including where the default is off. `?consent_geo=` is honored only when `VERCEL_ENV` is not `production`. The product app has no cookie banner; its Meta Pixel stays on `/join` when conversions are on, and Google Ads stays off the app. Vercel Speed Insights stays ungated. Browser Purchase, and any later browser Lead or InitiateCheckout that checks `readConsent()`, follow this decision. The pixel still does not sit in the server HTML.

- **No fixed parent-facing copy.** A model writes replies from facts the code supplies. A missing fallback sentence is intended: when the model fails, the turn holds and the failure is a named, logged outcome.
- **No keyword or regex reading of parent messages, STOP included.** Intent comes from model readings. Pattern checks on Hale's own outgoing text (a link gate, a number check) are fine.
- **Email alert once (`EMAIL_ALERT_ONCE_ENABLED`, VIL-762).** Default off. Env-only. On only for exact `true`. The model decides whether two emails are the same who, when, and where, and whether the visit clashes with a commitment Hale already holds (a calendar row this parent accepted, this parent's booking, or an email already told, including a no to the calendar add). Code checks the returned ids are ones it handed over. It does not compare titles, places, or times. A cancellation is not judged. A move is not suppressed as a repeat. Same visit: nothing sent. A clash is named inside the one notice; if that notice cannot be written, nothing is sent and #ops is paged. Teen mail stays on the per-thread key, and a 13+ child's calendar row is not a commitment. Another parent's booking is not. An unanswered invite is not. A booking the provider cancelled is not. Off, the per-thread key is unchanged.
- **No numeric send caps.** The model and the decider choose timing and volume. The code rails are intended: opt-out, quiet hours, same-item dedupe, provider rate limits and line health.
- **Absence is a first-class outcome.** A dependency that may be missing is logged and named in the return value (for example `skipped: 'not_configured'`). **Do** flag a silent no-op, or an absence folded into an outcome that means something else.
- **Production text gate (VIL-696).** Before a `hale-web` production deployment is aliased, one signed `CANARY` inbound from the synthetic probe number is posted at that deployment's own URL. The reply is the `sms_canary_answered` audit row stamped with `VERCEL_DEPLOYMENT_ID`. The handler sends nothing and calls no model. Holding the alias is Vercel's Deployment Check on the commit status `Vercel - hale-web: prod-text-gate (production)`, not a `vercel promote`. A failure pages #ops once and opens one GitHub issue. The route is not a Vercel cron. Recorded decision: the probe is the existing canary line, not a live Linq send to a parent phone.
- **Fail closed.** When identity, audience, time zone, place or consent is unknown, Hale holds or asks instead of guessing.
- **Tests and models.** Model behaviour is tested with cached real recordings through the eval harness, never with mocked model output. The repo's convention allows a fake at a client port that tests request mechanics only and says so (for example `apps/web/lib/testing/kid-judge-client.ts`). **Do** flag a stub that stands in for the model's judgement.
- **Recorded decisions.** A limit that the PR body, a ticket or a comment records as a decision ("Known limitation", "Stated limit", a design ruling) is not a new bug. Flag it only when the stated limit is wrong or the code exceeds it. A recorded decision never exempts a hard rule.
- **Migrations** are hand-written, additive SQL in `packages/db/drizzle`. A missing *generated* migration is intended. A schema change without its hand-written SQL is a bug.
- **Dark features.** Code behind a flag that is off is still reviewed; say in the finding that it is behind a flag.
- **VIL-728 group loop guard (`GROUP_LOOP_GUARD_ENABLED`).** Default off, exact `true`. It is a rail against a bot loop, not a send cap on people: a sender whose number is a verified Hale channel is never held. After `GROUP_LOOP_GUARD_CAP` Hale group messages (default 5, last 30 minutes, counted from `channel_messages`) with no verified person speaking, Hale answers no unverified sender in that chat until a verified person speaks. Quiet sends nothing and announces nothing; an opt-out still goes through. Who spoke and how much Hale said decide it, never the words. Proactive sends are not held. Reactions and poll votes are not guarded (Linq names no reactor). A guard that cannot read logs `group_loop_guard_unread` and the turn runs unguarded, like the other rate rails.
- **VIL-704 plan open, season slot, city login.** Three env-only flags, each on only when the value is exactly `true` (`true\n` stays off). Nothing in PostHog may turn them on. `REGISTRATION_PLAN_AT_OPEN_ENABLED` claims a plan at `plan_opens_at`. Recovery of an unstarted claim leaves a live lease alone. `SIGNUP_HELP_SLOT_RELEASE_ENABLED` returns a Plus/Free season slot on a pre-session throw or a `rush` page; a provider-side failure still counts. `PLAN_CITY_LOGIN_OWNER_ENABLED` refuses a co-parent plan the other parent's city password and captured session, and the day-before prep asks that parent for their own login. There is no share grant and no new parent copy. Browser Use `secretBindings` stay as they are. Off, today's early claim, burned slot, and family-scoped login remain.
- **Ask policy (`ASK_POLICY_TIERS_ENABLED`, VIL-719).** Default off. On only for the exact value `true`, read per family. The table is `docs/ask-policy.md`, held to the code by a test. When it is on:
  - An ask-first kind (money, a registration or booking, a third party, another person's information) never runs without the `action.approved_by_human` row. It is held at the `ask_first` gate, re-gated on resume, and refused at the `executeAndRecord` door. A refusal hands the draft back to the parent (`reviewed`); it is not an execution failure.
  - `send_email`, `reply_to_email`, `share_photos_with_family`, `create_calendar_event` and `update_calendar_event` stop being autonomous. That is intended tightening.
  - No streak grants an ask-first kind, and its turn-on text is withheld.
  - An execution run as just do owes no on-its-own text.
  - Both of those are decided per family when the dispatch runs, so turning the flag off makes them owed again.
  - A tell-after text the model cannot write sends nothing and pages #ops; the action stands.
  - A coach calendar change the parent asks for still waits for their yes. VIL-719 names that flow as tell after and it is not built; Barton has not ruled (`docs/ask-policy.md`). Do not treat the wait as a decision.
  - The email to a provider after a plan's options did not match needs a `provider_email_yes` audit row, written first. No row, no email.
  - On a pass with no approving parent, a `calendar_*` action whose Google leg would write to a calendar whose owner does not hold the kind is ask first (`writesAnotherParentsCalendar`). A failed read of that owner holds the same way (`calendarOwnerUnread`).
- **Max entitlements (`MAX_ENTITLEMENTS_ENABLED`).** Default off; do not turn it on from a PR. Env-only exact `true` — nothing in PostHog may turn this on. Off, Max (`family`) unlocks exactly what Plus does (VIL-131 still holds for autonomous execute). On, Max gets 8 web searches per `find_activities` call and 4 calls per turn (Plus stays 3 / 2), a 20 live-watch cap (Plus 8; flag off is uncapped), Browser Use signup help (Plus 2 per registration season, Max unlimited; at the Plus cap, connector/Playwright stay and the reply model writes from used/cap/resetsOn), and a counts-only Priority support line on the daily #ops post (Max families sort first; no family ids). Limit-hit replies are model-composed from those numbers. Watch-cap tool results name the live count and the cap; they are facts for the model, the same class as the other `watch_for_opening` refusals, not a Langfuse prompt (channel tools do not load prompts by name). A request for a class the household already watches does not consume a slot. The cap is best-effort against two parents adding different watches in the same moment: inbound work serializes per parent, not per household, and spot watches arm after the parent is told (SEND-TIME ONLY). Recorded limit. No parent-visible plan name, upgrade prompt, or template copy.

- **VIL-721 in-thread onboarding (`THREAD_ONBOARDING_V2_ENABLED`).** Default off, env exact `true`, and on only with `COLD_START_LADDER_ENABLED` (the friend walk it rides). Lit, the walk is postal, kids, ages, the map, the kids' activities, name, ONE Google link, schedule, co-parent. The one link (`/connect?to=google` → `api/integrations/google/connect`) opens ONE Google consent for the Gmail and Calendar read scopes together, so the parent meets the unverified-app screen once. That is intended and is not a regression of the self-scoped grant in `buildGoogleAuthUrl`: since VIL-156 every disconnect path ends every Google connector of that parent and revokes its tokens (Google revokes per project), so a token holding both scopes leaves Hale nothing a disconnect does not end; `include_granted_scopes` is still never set. Each granted connector is stored as its own row holding the same token, the row's scopes are the token's, and a box left unticked stores only the other; neither ticked is `partial` with a fresh ONE link. The callback completes a bundle consent already in flight when the flag is turned off (state TTL 10 minutes): the parent granted it. The kids' activities come only from the model's `activities` field and are kept as `routine` family memory facts keyed without a colon (so `factsForContext` reads them), with provenance on the row and one counts-only `onboarding_activities_kept` audit row; code adds no name to the value, and an activity whose words name a 13+ child it cannot be placed on is not kept. The one Google ask rides the ledger's existing `calendar` send class with its own `google` ask key (the class column is CHECK-constrained). The unverified-app screen reaches the model as `GOOGLE_UNVERIFIED_APP_FACT`, never as a sentence. The bundle landing and done pages reuse the Gmail and Calendar page strings. The flag is env-only, so no PostHog sync can light it. The consent asks for the two read scopes and the profile, never a write scope. A bundle state is single-use: the callback checks the signed-in parent and family, then spends the texted link before it exchanges the code, and a state with no live link is refused. Every text this walk adds (card, fresh link, receipt, the ask on it) is recorded as sent only after Linq accepts it, with the claim row's id as Linq's key (`connect/google-send-receipt.ts`); a certain refusal frees the key and an unclear failure keeps it, and stop, erasure and line hold are read right before the send. A connect by one parent never reads or writes the other parent's open onboarding session. The only name match on a kept activity is the teen privacy gate; which kid it belongs to is the model's field. A bundle grant whose Google account cannot be identified (profile box unticked, or the read failed) is stored nowhere, so the co-parent check never runs blind. While lit, an open walk hands a disconnect or a new-link ask to the router's existing handlers (main's `detect.ts` picks the turn; a disconnect still acts only on the model's read).

## Ignore

- `apps/worker/evals/cache/**` and `apps/web/lib/__journey__/__recordings__/**`: recorded model output.
- `apps/web/lib/channel/off-domain/postal-cities/ca.json`, `postal-cities/us.json`, `apps/web/lib/channel/off-domain/public-suffix/suffixes.json` and `public-suffix/public_suffix_list.dat`: generated or vendored tables.
- `pnpm-lock.yaml`.

Not ignored, even though it looks like data:
- `apps/web/lib/channel/off-domain/postal-cities/coarsen.json` is the privacy allowlist of place names that may go to third-party search on a sensitive question. A small town moved onto it would reveal where a family lives.
- `apps/web/lib/channel/intake/postal-zone.ts` is hand-written logic.
