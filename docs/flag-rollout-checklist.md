# Staged enablement checklist

VIL-405, corrected in VIL-557. Merging this page leaves every flag where it is.

This page says what each flag does, how its value is parsed, what the code does when it is unset, which flags depend on which, the order to light them in, the probe, and the rollback and kill. It never says what a flag holds in any environment or whether it is set. The live production values are recorded privately in Linear (the 2026-11-03 flag table on the document ["Product direction 2026-09-21"](https://linear.app/villagehale/document/product-direction-2026-09-21-the-activity-finder-loop-read-before-bca7b5c32d03)) and must never be copied into this repo, its pull requests or its commit messages.

Parsers cited at origin/main `1017409437f8`. `apps/worker` reads one product flag, `AUTONOMOUS_EXECUTE_ENABLED`, in the orchestrator that `apps/web` runs from `/api/cron/drain`. Eval scripts read `EVAL_GATEWAY_MODEL` only when someone runs an eval.

Kill switch, every time: set the value on the Vercel production project for `apps/web`, then redeploy that project.

Launch flags are also catalogued in `@hale/flags` and evaluated through `isEnabled` / `flagValue`. `POSTHOG_FLAGS_ENABLED` is off unless exactly `true`; while off, every reader is today's env parser. Once on, an explicit env `false`/`off` (or `VOICE_DISABLED=true`) kills the flag regardless of PostHog; otherwise the family-hashed local PostHog flag is used, and a miss falls back to the env value. `BROWSER_USE_SIGNUP_PAYMENT_ENABLED` and `LINQ_APP_CLIP_PAY_ENABLED` stay env-only. Sync PostHog with `pnpm posthog:sync-flags -- --dry`.

`true` means the value is exactly `true`, with no extra characters. `trimmed true` (written `true` (trimmed)) means trim, then exactly `true`. `on` means trim, then exactly `on`. `on` (no trim) means exactly `on`, with no trim (`SOCIAL_WATCHLIST`). `true`, `ON`, and `1` do not turn an `on` flag on.

The Unset column says what the parser does when the variable is unset:

- `ON` / `OFF`.
- `current`: a model-mode flag; the default model runs.
- `voice runs`: `VOICE_DISABLED` is inverted; unset, voice compose runs.
- `off` mode: `PROACTIVE_CADENCE` resolves to its `off` mode, the current send path. It is a mode, not an on/off flag. `REGISTRATION_DATE_CHECK` works the same way: unset is `off`, and no registration page is read.
- `200 USD (code default)`: `ANTHROPIC_SPEND_ALERT_USD` is config, not a flag.
- `no runtime chosen`: `SIGNUP_BROWSER_RUNTIME` picks no signup browser runtime.
- `OFF (preview-only)`: off, and it can only turn on in a Vercel preview.
- `no reader on main`: no source on main reads the variable; a stored value does nothing.

The four lane switches (VIL-226) hold work while they are off. They do not delete it. Like every other `true` flag above, the value must be exactly `true`: a piped `echo` stores `true` followed by a newline, which keeps the lane off. Set it with `printf '%s' true`, then redeploy. `TRAVEL_BRIEF_ENABLED` is read through the same helper under its own name.

- With `CALENDAR_ALERT_ENABLED` unset, both the 1:1 calendar text and the Linq household calendar notice are off. The sweep still remembers each change. A calendar text Hale already owes stays owed and is offered again when the lane is back on. One older than the usual pending limit is aged out by the lane-off sweep itself (`pending_expired`), so its held title and location are cleared on time. Kid events not yet told to the group stay unannounced until then. Passport stamps inferred from calendar changes follow this switch too: with the lane off no calendar stamp is written, even with `INTEREST_PASSPORT_ENABLED=true`, and the sweep returns `passport: 'lane_off'`. This includes a seeding run (a connection's first sync, or a full resync Google forces after a stale sync token).
- With `PARENT_CALENDAR_MIRROR_ENABLED` unset, mirrored `family_events` rows stay in the database and no new reminders are created for them (counted as `notScheduledLaneOff` in the reminders cron response). Reminders already scheduled stay `scheduled` and are counted as `heldLaneOff`. The connector sync logs the held window with `heldReason: 'lane_off'`.
- A reminder whose time passed (held by a lane, or late after a cron gap) is never turned into `missed` by a time window. When it is next classified it is sent if its event has not started (counted in `firedLate` beside `fired`), an evening-before reminder on the event's own day included, and dropped as `started` once the event has begun. A reminder opens with its event's own local date, never a word like "tomorrow", and the voice phrases the day from the event's local start and the send moment. Each drop is logged as `reminder: dropped, not sent` with its reason and writes a `reminder_suppressed` audit row. The per-family send decider (#859) does not classify reminders, so this rule decides.
- With `REGISTRATION_LADDER_ENABLED` unset, the registration-sequence cron runs no ladder and answers `{ lane: 'registration_ladder', outcome: 'lane_off', groupSync: 'lane_off' }`. The sequence rows are left as they are, so a leg whose window is still open goes out once the lane is back on. The group-decision flush in the same route is held too: those syncs send group bubbles.
- `REGISTRATION_PLAN_RUN_ENABLED` carries out a parent's day-before registration plan at the open and pays with the card saved on the parent's city account. The payment also needs `BROWSER_USE_SIGNUP_PAYMENT_ENABLED` exactly `true`; without it the plan stops at checkout with `payment_off` and the parent pays on the live browser. Before paying, a read-only checkout review in the same browser chooses the saved card and stops on the last page before "place order"; code checks the total read there against the maximum and the spending cap and pays only that exact total. A review that says it placed the order ends `review_placed_order`, keeps the browser open, writes a `plan_payment` row with no amount, and pages Slack #ops (`registration_review_placed_order`, ref = the offer id). **Do not arm it while Browser Use can solve a CAPTCHA on a plan run.** Hale never solves or gets around a CAPTCHA (2026-11-04 decision). Plan runs are Browser Use V4 agent runs. Browser Use solves CAPTCHAs on agent runs by default, and V4 run `browserSettings` has no `solveCaptchas` field (https://docs.browser-use.com/cloud/browser/captcha-handling). A run cannot attach to a browser Hale created with `solveCaptchas: false`, because `POST /runs` takes no browser id. Arm it only after one of these: Browser Use confirms in writing that solving is off for Hale's project, or V4 adds a run-level `solveCaptchas` and the plan engine sends `false`. Browser Use's EU deployment has solving off, but moving there needs a data-residency decision under hard rule #1, so it is not a quiet switch. A plan whose parent no longer stands behind it ends `cancelled` with `authorization_lapsed` and texts no one. That covers a parent who opted out, left the family, or has an unread text held as a possible stop, and a family scheduled for erasure. The check runs at the claim and again just before payment. The same switch also turns on the day-before plan conversation (the plan offer, the parent's yes or take-back) and the `/api/cron/signup-plans` minute cron; unset, the cron answers `skipped: 'flag_off'` and the conversation leaves every offer to the one-shot sign-up.
- `EMAIL_ALERT_ENABLED` holds the parent 1:1 text and the silent booked-detection backfill. With the lane on, Hale tells the parent what a parenting email says, in their 1:1. The backfill still sends no text; its `activity_bookings` rows feed how-it-went texts. With the lane off the backfill does not start a page, logs `booked detection backfill: email lane off, page not started`, and stamps nothing, so the page is read when the lane is back. `BOOKED_DETECTION_BACKFILL_ENABLED` keeps its own meaning. This coupling stays until the VIL-226 kid check runs in the backfill path.
- `EMAIL_ALERT_BODY_ENABLED` lets that 1:1 writer read the Gmail body for that one compose. Off (unset) is today's facts-only writer and does not re-key the notice eval. On, a second Gmail fetch is fenced as untrusted data, used for that compose, stripped of email-only links/phones/codes, and dropped: no DB, log, trace, or PostHog property holds it. Teen and private mail stay facts-only. Needs `EMAIL_ALERT_ENABLED`.
- With `EMAIL_ALERT_ENABLED` unset, the Gmail ingest cursor (`historyId`) still advances, and a second watermark, `alertHistoryId`, stays where the lane went off. The sync logs `connector sync: gmail alert watermark` with `gmailCursor: 'held_lane_off'`. When the lane is back on, the held mail is released in that sweep and never dropped (`released`). A pass that throws leaves the watermark in place (`release_failed`) and the next sweep retries it. A history read that stops at its page limit carries the last record it reached forward as the watermark (`releasing`). Only if Gmail no longer has history that far back is the watermark dropped as `held_expired`, and that mail is not alerted.
- There is no per-family or per-sweep count on how many messages a lane may send. The lane switch is the stop. A calendar change older than the pending limit is still aged out (`pending_expired`), because a three-day-old "it moved" is no longer the week.

## What to watch

Same checks for every row below, for the first seven days after it is confirmed on:

- `channel_messages.status`: `failed` against `queued`, `sent`, and `delivered`.
- `audit_log.action_taken` = `sms_turn_failed`.
- No-reply gap: an outbound ask with no inbound from that parent for 24 hours.
- Latency: inbound `channel_messages` row to the matching `sms_turn_answered` audit row.
- Opt-outs: a parent STOP, a new `email_opt_outs` row, or `same_activity_opt_in_revoked`.

One extra signal is named on the row.

### Lighting order

1. Apply the prerequisites a flag names (a migration, a key, a webhook subscription) before lighting it.
2. Light a flag only after the flags it depends on (below).
3. Light one flag at a time, during a week when Noah is watching the five families. Its owner lights it.
4. Rows in [Light last](#light-last) wait for their own condition. Keep the rows marked "hold for the first five families" off for those families.
